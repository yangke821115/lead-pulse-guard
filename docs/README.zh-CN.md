# Lead Pulse Guard

**每一条线索，都进同一个队列。由人来决定。**

Lead Pulse Guard 监控 Facebook 评论、广告线索表单和邮箱三个入口，用大模型起草回复或摘要，然后推一张卡片等人工确认。**没有任何内容会自动发给客户。**

大多数评论自动化工具是全自动的。餐厅回一句「谢谢惠顾」没什么问题。但如果问的是交期、认证或者价格，让模型自己去答就很危险——它会编一个听起来很合理的数字，而这个数字现在就挂在公开评论区，署着你公司的名字。

所以这个项目只围绕一条规则运转：**模型提议，人拍板。**

## 01 — 为什么做这个

自动回复会出错的三种方式。下面三种在这里都是靠结构解决的——**由代码直接拒绝执行，而不是在提示词里请求模型「请勿」**。

| 失效 | 没有护栏会发生什么 | 怎么拦住 |
|---|---|---|
| **机器回环** | 机器人回复了一条评论，这条回复又以新事件的形式回到 webhook，机器人于是回复自己，如此循环，永不停止。 | 身份校验：评论者若是自家主页，该事件直接不具备回复资格。 |
| **礼貌死循环** | 客户说声「谢谢」，机器人回一句；客户再说「好的」，机器人再回一句。谁的问题都没被解决，话头也停不下来。 | 收尾语过滤：整句匹配而非包含匹配，且问句永远优先。 |
| **一本正经地编** | 被问到一个它并不知道的参数时，模型会给出一个看起来很合理的数字。 | 知识库门禁：不在「已确认事实」里的内容，模型不得作出任何具体陈述，只能转交人工。 |

这三种问题在提示词层面是止不住的。模型并不知道自己「不知道」，而循环是事件结构本身造成的——一条自动回复，天然就是一条新的输入。

## 02 — 三个入口，一个审批出口

名字就是需求：**别让进来的线索掉在地上。**

实际上，一个 B2B 卖家被找上门的渠道有三个，互不相关，投递机制不同、失效方式不同、对「一条消息」的定义也不同。

| 入口 | 以什么形式到达 | 投递方式 | 静默失效方式 |
|---|---|---|---|
| **主页评论** | `feed` / `comment` / `add` | webhook | 会漏；自家回复被当成新事件送回来 |
| **广告线索表单** | `leadgen` 事件 + 一次 Graph 拉取 | webhook | **事件根本不投递**——表单填满了，没人被通知 |
| **邮箱** | IMAP 里的一封 MIME | 轮询 | 只要轮询在跑，就不会漏 |

第三列才是真正咬人的地方。**一个不再到达的 webhook，看起来和今天没人来一模一样。**

```
                         Facebook                       Mailbox
            ┌────────────────┴──────────────┐               │
            │ 评论                 广告线索  │               │  IMAP
            │ feed webhook          leadgen  │               │  只读，
            └────────────────┬──────────────┘               │  从不标已读
                             │                               │
        ╔════════════════════▼═══════════════╗   ╔═══════════▼═══════════╗
        ║  gateway                           ║   ║  邮件轮询器            ║
        ║  对原始请求体验签                   ║   ║  垃圾邮件分类          ║
        ║  主页打标 → 去重 → 资格判定         ║   ║  按内容分业务线        ║
        ╚════════════════════╤═══════════════╝   ╚═══════════╤═══════════╝
                             │ 只追加的 JSONL                │
                             ▼                               ▼
        ╔════════════════════════════════════════════════════════════════╗
        ║  worker                                                        ║
        ║    评论 → 该主页的知识库 → 起草回复                             ║
        ║    线索 → 打分 + 分流 → 写表格 + 推卡片                        ║
        ║    邮件 → 摘要 + 分流 → 推卡片                                 ║
        ╚════════════════════════════════╤═══════════════════════════════╝
                                         │ 审核卡片
                                         ▼
                                    人工
                                         │ 发送 / 改后发送 / 忽略
                                         ▼
                              Graph API ──► 以主页身份发布
```

三条链路汇到同一张卡片：原始消息、模型草稿，以及一个可以「发送 / 改后发送 / 忽略」的人。**任何渠道、任何情况下都不会自动发布。**

### 为什么网关和 worker 之间不走网络

网关只往文件里写一行 JSON，worker 去 tail 它。这意味着：

- 网关**不持有任何下游凭据**。
- 攻破网关，攻击者最多也只能往一个 spool 文件里写一行字。
- worker 可以随时停、重写、替换，webhook 端点完全不受影响。
- 每一条事件都落在磁盘上，都能重放。

判断一个新增交接点是否安全，要看**它给现有服务增加了什么能力**：写文件不增加任何能力；开端口增加入站面；发起 HTTP 增加出站面。功能相同时，选增加能力最少的那个。

### webhook 不是投递保证，所以还有第二条路

我们实测过一天：进来 5 条广告线索，**只有 2 条产生了 webhook 事件**。另外 3 条在 Meta 那边确实存在，我们完全看不见。没有报错，没有日志，也没有重试——从接收端看，**链路断了和今天没人来是一样的**。

所以每个吃 webhook 的渠道都另外配了一个轮询器：

```
        webhook ──┐
                  ├──► 同一个幂等入口 ──► 一张卡片，绝不会有两张
        poller  ──┘     （按活动 ID 原子占位）
```

- **线索轮询**——每 10 分钟，列出表单、翻页取提交、把本地还没占位的喂给同一个处理函数。和 webhook 完全同一条代码路径，所以打分、分流、卡片格式全都一致。
- **评论轮询**——思路相同，但它**不复制资格判定**。它把评论重新签名、当成一条 webhook POST 回网关，于是自家主页过滤、去重、收尾语逻辑在全系统只有一份实现。

占位是原子的，谁先到谁赢，另一条路自动变成空操作。轮询**不是 webhook 的替代**——webhook 仍然更快。轮询只是把最坏情况从「永远收不到」压到「最多晚十分钟」。

## 03 — 包含什么

核心设计是「拒绝执行」。以下每一项都在仓库里，设计理由写在 `docs/` 中。

**网关（`gateway/`）**

- [x] 对**原始请求体**做 `X-Hub-Signature-256` HMAC 验签
- [x] 定时安全比较（`hmac.compare_digest`）
- [x] 拿不到 App Secret 就拒绝启动——绝不退化成「接受未验签流量」
- [x] 按显式注册表给事件打主页标记
- [x] 重复投递抑制（`comment_id:verb` + TTL）
- [x] 线程深度上限（默认 3）
- [x] 自家主页过滤（防机器回环）
- [x] 收尾语过滤，问句优先（防礼貌死循环）
- [x] 只追加的 JSONL spool，带大小上限与轮转
- [x] **整个代码库中没有任何出站 HTTP 调用**

**worker（`worker/`）**

- [x] spool tailer，偏移持久化（重启不丢、能处理轮转）
- [x] 线索链路：字段提取、打分、业务线分流、可选的表格写入
- [x] 表单选项映射放在外部 JSON——源码里没有客户的字段名
- [x] 按主页加载知识库
- [x] 模型重试链：便宜池优先，付费兜底
- [x] 严格 JSON 输出，自带检查项（`answers_question`、`invented_specifics`）
- [x] 先应答、再执行的回调处理——超时会让人再点一次，然后就发了两遍
- [x] 演练开关，默认开启

**兜底轮询（`worker/leadpoll.py`、`worker/commentpoll.py`）**

- [x] 线索轮询：列表单 → 取提交 → 把尚未占位的全部喂进流水线
- [x] 评论轮询：把每条评论重新签名成 webhook 投回网关，资格判定只留一份
- [x] 按活动 ID 原子占位——webhook 和轮询会抢，最终只产生一张卡片
- [x] 两者都有 `--dry-run`：只报告缺了什么，不处理

**邮件通道（`worker/mail.py`）**

- [x] 只读 IMAP 轮询，全部用 `BODY.PEEK` 取信，不标已读、不移动、不删除
- [x] 先做垃圾邮件分诊，再按**内容**而不是按收件箱分业务线
- [x] 跨重启去重（UID 水位 + Message-ID 集合），首次运行只建基线，不倒灌历史
- [x] 识别我方发出的邮件，不把自己的回信当成新线索

## 04 — 快速开始

**默认就是演练模式，装完不会往 Facebook 发任何东西。**

```bash
git clone https://github.com/<you>/lead-pulse-guard.git
cd lead-pulse-guard

cp .env.example .env
# 填 META_APP_SECRET、META_VERIFY_TOKEN
cp pages.example.json pages.json
# 填上你的真实主页 ID
```

先只起网关，确认能收事件：

```bash
docker compose up -d gateway
docker compose logs -f gateway
```

把 Meta 应用的 webhook 指向 `https://你的域名/webhook`，然后**在两个层级都订阅** `feed` 和 `leadgen`——App 级**和**主页级。

> 这一条几乎所有人都踩过：只配主页级、或者只配 App 级，另一层看起来完全正常，但事件根本不会投递。详细步骤见 [`docs/security.md`](security.md)。

然后起 worker：

```bash
python3 -m venv venv
./venv/bin/pip install -r worker/requirements.txt
./venv/bin/python -m worker.main
```

> 唯一的第三方依赖是 `lark-oapi`，其余全部是标准库。项目自带一个极简的飞书 SDK 垫片，避免官方 SDK 在 import 时加载全部 REST 端点（实测可省约 120MB 常驻内存）。

`AIW_POST_ENABLED=false`（默认值）时，点「发送」只会显示「模拟发送」，什么都不会发到 Facebook。**看过几条真实草稿之后**，再改成 `true`。

### 语言

回复跟随评论者的语言。评论看不出语言时，用 `pages.json` 里该主页的 `language` 兜底。

提示词、代码、注释、日志全部是英文（`worker/prompts/*.en.txt`）。审核卡片默认英文，设 `AIW_CARD_LANG=zh` 可切成中文。写进数据库的枚举值两种语言下都保持中性，读取时也兼容更早的中文取值。

### 什么情况下我们会劝你别买

- 没人能每天花十分钟看队列——那会把「偶尔漏回」变成「系统性地不回」
- 产品参数还没落到纸面上——**模型的安全边界就等于你知识库的质量**

## 07 — 不做什么

这不是聊天机器人，不是 CRM，也不替代销售团队。

它也不做线索抓取，不碰 Instagram 私信，不尝试绕过任何平台的限流。

**它不做的事，和它做的事一样重要。** 一个「什么都能干」的自动化工具，最后通常是什么都干不好，而且出了问题没人说得清是哪一层的责任。
